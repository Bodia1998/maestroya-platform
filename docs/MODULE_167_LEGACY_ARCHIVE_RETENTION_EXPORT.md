# Module 167 — Legacy Archive & Retention Export

Status: implemented on `feature/module-167/legacy-archive-retention-export` (base: M166 merge `b6a172f`). **Verdict: ENGINEERING SCOPE IMPLEMENTED — MODULE NOT COMPLETE, BLOCKED BY DECISIONS AND BY NOT HAVING BEEN RUN AGAINST A REAL DATABASE.** Default behaviour of the application: **unchanged**. This module adds a **read-only, deterministic, self-verifying export** of the legacy (`flowVersion = LEGACY_QUOTE_PAYMENT`) financial and contractual history, and a database-free verifier for the result. It changes no legacy behaviour, adds no schema, migration, environment variable, feature flag, route or cron, deletes nothing, disables nothing, performs no production export, and **does not claim Gate D**. It is not legal, tax or accounting advice, and **it defines no retention period**.

## 1. Scope and explicit non-goals

M167 prepares the irreversible steps that follow (M168 code removal, M169 schema retirement) by making the legacy history exportable, checkable and explainable *before* anything is removed.

Built (all read-only toward the database): a declarative inventory (`domain/services/legacy-archive-spec.ts`), pure build + verification logic (`domain/services/legacy-archive.ts`), a query-only port (`domain/repositories/legacy-archive-reader.ts`), a Prisma adapter reading in one `READ ONLY` / `REPEATABLE READ` transaction (`prisma-legacy-archive-reader.ts`), a two-phase store port with a local-filesystem adapter (`application/ports/legacy-archive-store.ts`, `infrastructure/legacy-archive/fs-legacy-archive-store.ts`), an export use case and a verify use case, an argument guard, two plain-factory composition roots, and one operator script (`npm run legacy-archive-export`).

Non-goals (kept intact, in this order):

- **M168** — Legacy Code Removal: not done; no legacy code, route, webhook, cron or subscriber was removed or disabled. **M169** — Legacy Schema Retirement: not done; no table, column or enum was touched. **Gate D** — not claimed.
- No production export was run, no database was connected to, and no real data exists in any test, fixture, log or committed artifact.
- No restore/import tool. The archive is an *evidence extract*, not a database dump (blocker **B6**).
- No retention period, notice period, deadline or legal conclusion is invented (blocker **B1**).
- No change to LEAD_V1, M132 pilot categories, M159 `LEAD_V1_ROLLOUT_MODE`, M164/M165 routing, the M166 report or any production flag.

### 3.2 Distinguishing mandatory evidence from what can be excluded

*Mandatory* categories are the contract and money chain a reconciliation or tax review has to walk: request → quote → job → payment → commission / refund / payout / adjustment / ledger transaction → invoice / credit note → reconciliation record → affiliate derivation. *Supporting* categories (appointments, dispute evidence metadata, counters, webhook ledger, audit entries) explain but do not carry amounts. Whether a *Mandatory* category may instead stay in the database (read-only) is the roadmap's open decision (**B10**); this module only guarantees the extract is complete and verifiable.

## 4. Format, manifest and integrity guarantees (as implemented)

An archive is a directory with: one `<category>.ndjson` per category (28 files, an empty file for an empty category), `manifest.json` and `SHA256SUMS` (standard `shasum -a 256 -c` format).

- **Deterministic.** Rows ordered by primary key (the composite `series/year` for counters); JSON keys in the order declared in the spec; money as exact 2-decimal strings; timestamps as UTC ISO-8601 with milliseconds; booleans and integers as JSON. The same data yields **byte-identical category files** and the same `archiveDigest` on every run; only `generatedAt` differs (tested). Input order is irrelevant (tested with reversed input).
- **Versioned.** `format = maestroya.legacy-archive`, `formatVersion = 1`, `module = M167`. The verifier refuses an unknown version.
- **Manifest.** Generation timestamp; the options used; per category: title, file, evidence class, `recordCount`, `tableTotal`, `outOfScopeCount` (= rows in the table that are not in the legacy scope — **never hidden**), `bytes`, `sha256`, whether an independent database control existed, the exact field list, and exact money totals **per field and per currency** (never netted, never mixed); `totalRecords`; `archiveDigest` (SHA-256 over format, version, options and each category's key / count / hash); the retention statement (`periodsDefined: false`, `UNRESOLVED_D20`); every blocker; every exclusion.
- **Exact money.** Integer cents (BigInt); no floating point anywhere. Anything that is not an exact 2-decimal value is rejected, never rounded. Currency is preserved on every row that has one; rows without a currency column are totalled under `NO_CURRENCY_ON_RECORD` (their currency is that of the parent payment, quote or invoice).
- **No silent omission or truncation.** (1) Per-category ceiling (default 50 000 rows): exceeding it aborts. (2) For every category scoped in the database the reader asks the database *independently* for the row count and exact sums over the same filter, and the builder aborts on any difference. (3) `affiliate_*` and `audit_logs` are scoped in memory after a full scan, so they have **no independent database control** (shown as `n/a` in the run output and `controlled: false` in the manifest); they are protected by the ceiling and by reference checks only.
- **Read-back verification.** After building, the archive is verified in memory; it is then written to a private staging directory, **read back from disk**, verified again and required to be byte-identical to what was built. Only then is it published (atomic rename). Any failure discards the staging directory and exits non-zero; there is no "partial success" result.
- **Verifier (no database, no environment).** Checks: manifest structure and version; exact file set; SHA-256 and size per file; `SHA256SUMS`; record counts; strictly ascending unique keys; exact field set and value formats per record; every non-null reference resolves inside the archive; exact totals recomputed from the records; `totalRecords`; `archiveDigest`. Issues name codes, categories, line numbers and record ids — never values.
- **Provenance and traceability.** Every record keeps its original primary key and all relationship ids, so each archived amount traces back to its source row (`stripePaymentIntentId`, `stripeRefundId`, `stripeTransferId`, `stripeDisputeId`, `invoiceNumber`, `creditNoteNumber`, `documentHash`, `caseNumber`, webhook `externalEventId` are kept as business identifiers). Customer, professional and user ids are kept as opaque pseudonymous ids (their profiles are not exported).
- **Reconciling and explaining history.** From the archive alone one can walk payment → refunds / payout / commission / ledger transactions / adjustments / invoice / credit notes, recompute per-currency totals, compare them to the manifest, and see the reconciliation runs and discrepancies recorded at the time. Net position per invoice (invoice total minus credit notes) is computable from the data; the module does not publish a "reconciled" verdict.

## 5. Retention assumptions and unresolved legal decisions

**Assumptions.** (a) Until D20 is decided, the database remains the system of record; the archive is an additional, verified copy. (b) Nothing may be deleted, dropped or purged on the strength of an archive produced by this module. (c) Retrieval = run `npm run legacy-archive-export -- --verify <dir>` (or `shasum -a 256 -c SHA256SUMS`) and read the NDJSON files with any JSON tool; no MaestroYa code is needed to read them. (d) Pseudonymous ids in the archive can no longer be resolved to a person once the corresponding profile is erased under the GDPR rules — an intended consequence of excluding profiles.

**Not decided, therefore not implemented (no period is invented):** minimum and maximum retention periods for financial, dispute, audit, consent and affiliate records; whether an automatic purge is required; whether the archive format is acceptable evidence; whether invoice party identity and free-text explanations must travel with the archive. These require confirmation by the appropriate Spanish professional adviser (gestor / abogado) — see M116 L-10, B-07.

## 6. Security and sensitive-data handling

- **Authorization gate.** Export refuses to start unless `--authorize-database-host <host>` equals the host of `DATABASE_URL` (case-insensitive), `--output-dir` is an absolute path **outside the repository**, and every argument is known and given once. Messages never echo the connection string, credentials or either host. A stray `.env` therefore cannot silently aim the export at production, and production is read only when the operator says so deliberately. The tool is not wired to any route, Server Action, webhook, cron, queue or scheduler (static test).
- **Read-only toward the database.** `SET TRANSACTION READ ONLY` (the database refuses writes), `REPEATABLE READ`, only `findMany` / `count` / `aggregate` / `groupBy`, explicit `select` lists, no `include` (static + fake-client tests).
- **Write safety.** The only file writes are in `FsLegacyArchiveStore`: target must not exist (never overwritten); parent must exist; neither may be inside a Git work tree; files created exclusively (`wx`), owner-only (`0600`), fsynced, in a private staging directory (`0700`); published with an atomic rename after re-checking the target; published files `0400`, directory `0500`. The only deletion in the module is the removal of its own staging directory.
- **Data minimisation.** By default no party legal name, tax id, address, e-mail, free text, URL, IP address, user agent, JSON blob, referral code or idempotency key is selected, serialized, logged or printed. The URL of dispute evidence and the IP / user agent of self-billing acceptance and audit entries are never exported, even with the opt-ins.
- **Logging.** The script prints counts, hashes, file paths and blocker titles only; it never prints record contents. Non-domain errors print the error name and first line (≤ 300 chars).
- **What it cannot provide (B7).** Encryption at rest, write-once (WORM) storage, off-site copy, key management and access reviews. Put the target on an encrypted volume with restricted access; never commit it. Generated archives are personal-data-adjacent financial records.
- **No data in Git.** Tests use synthetic, sequential ids and round amounts generated from the spec; the export directory must be outside the repository and outside any Git work tree.

## 7. Operating it

```
# Export (operator only; read the safety notes in scripts/run-legacy-archive-export.ts first)
npm run legacy-archive-export -- --output-dir /secure/volume/maestroya-legacy-archive-<date> --authorize-database-host <host of DATABASE_URL> [--include-invoice-content] [--include-narrative]

# Verify any archive (no database, no environment); pin the digests recorded at export time
npm run legacy-archive-export -- --verify /secure/volume/maestroya-legacy-archive-<date> [--expect-manifest-sha256 <hex>] [--expect-archive-digest <hex>]

# Restore rehearsal into a DISPOSABLE PostgreSQL (loopback host, database name ending in "_test" or "_scratch"); rolls back unless --keep-scratch-schema
DATABASE_URL=postgresql://…@localhost:5432/<name>_scratch npm run legacy-archive-export -- --restore-rehearsal /secure/volume/maestroya-legacy-archive-<date> --authorize-database-host localhost [--keep-scratch-schema] [--expect-manifest-sha256 <hex>] [--expect-archive-digest <hex>]
```

Exit codes: `0` export complete and verified / archive verified; `1` verification found issues; `2` nothing could be produced (bad arguments, database or ceiling failure, integrity failure, existing target). "Complete" means the engineering export is complete and verified; it is **not** an approved retention archive.

## 8. Idempotency, retries and failure behaviour

Exporting reads one point-in-time snapshot and writes only into a directory that must not exist, so it has **no financial effect** and takes no lock. Re-running after a failure is safe: a failed run leaves nothing behind under the target name; a second run into an existing target is refused and leaves the first archive untouched; two runs over unchanged data give byte-identical category files and the same `archiveDigest`. A run that races with live writes sees a consistent snapshot and may be stale a moment later; the archive records `generatedAt`. Duplicate webhooks, retries, refunds and payouts remain governed by the existing mechanisms, which M167 does not modify.

## 9. Migration and rollback

No schema change, migration, environment variable, flag, route or cron. Deployment is inert: nothing calls the export except the script. Rollback = revert the M167 files and the one `package.json` script line. Exports already written are separate files outside the repository and outside the database; nothing needs undoing in the database.

## 13. Technical acceptance work after the review (2026-10-16)

Nothing here approves retention, defines a retention period or constitutes legal, tax or accounting advice. B1, B2, B3, B5, B7 and B10 remain external decisions; M167 stays **not accepted** and M168 must not start.

**Integrity: what the digests mean.** `manifestSha256` is the SHA-256 of `manifest.json`, which lists the hash of every data file, so it pins everything including `generatedAt` and metadata. `archiveDigest` is recomputed from the files over format, options and each category's key, count and hash, so it identifies the *data* independently of when the archive was generated. Without an outside reference a consistently rewritten archive verifies. `--verify` and `--restore-rehearsal` therefore accept `--expect-manifest-sha256` and `--expect-archive-digest`: the expected value is compared with the **recomputed** one (never the value the manifest claims), a pin that cannot be established counts as a mismatch, and the output states whether the run was pinned. Where the two values are kept (ticket, password manager, signed message from a second person) is owner decision B7; this change adds no signing key, cloud storage or encryption.

**Durability.** The staging directory is fsynced before the rename and the parent directory after it. If the parent fsync fails after the rename the CLI reports that the archive *was* published but is not confirmed durable (exit 2, code `LEGACY_ARCHIVE_PUBLISHED_UNCONFIRMED`) rather than "nothing was published". A leftover `.<name>.partial-*` directory from a killed export makes the next export refuse to start (it is never deleted automatically); an unrelated target's partial directory does not block it. Final permissions are unchanged (directory `0500`, files `0400`), but the order changed after a macOS failure: files are made `0400` first, the staging directory stays owner-only and writable (`0700`) through the pre-rename fsync and the rename, and is made `0500` immediately after the rename, before the parent fsync. macOS/BSD refuses to rename a directory that is not owner-writable (`EACCES`, even in the same parent); Linux does not, so the earlier order passed on Linux only. Between the rename and the `chmod` the published directory is owner-only with read-only files, so nothing becomes readable or writable by anyone else; if that `chmod` or the parent fsync fails the CLI reports published-but-unconfirmed (exit 2) and the archive is left in place for `--verify`.

**Restore / consumption decision.** The roadmap criterion reads "archive restores to a scratch database and passes row-count / checksum and invoice-total verification". Read-only inspection of the NDJSON files is not that, so a narrow rehearsal was built: `--restore-rehearsal` verifies the archive (and the pins), then loads it into **one new schema** (`legacy_archive_restore_<12 hex>`) of the database `DATABASE_URL` points at, with one table per category, archived columns only, identifiers as opaque text, and foreign keys only between categories that are in the archive. It runs in a single transaction and rolls everything back unless `--keep-scratch-schema` is given *and* every check passed. Guards: `--authorize-database-host` must equal the host, the host must be loopback, the database name must end in `_test` or `_scratch` (lowercase letters, digits, underscores; `maestroya_test` passes, `latest` or `contest` do not), and the schema name must not already exist. Checks come from the restored tables: row counts, exact `SUM` per currency over `numeric(20,2)`, PostgreSQL-enforced foreign keys, and a round-trip SHA-256 (rows read back, serialized as the exporter does, compared with the manifest hash), plus an invoices-minus-credit-notes report per currency. It imports no personal data the archive does not already contain, creates no users, profiles or other parents, and never touches the application schema.

What it does **not** prove: that the archive is complete for retention purposes, that it can be loaded into the application's schema, or that history may leave the database (B10). Whether an archive-shaped restore satisfies the criterion, or whether an application-schema restore is required, is an **open owner decision**; if the latter is required, the smallest next action is to name the parent entities (and whether pseudonymised placeholders are acceptable) in writing. B6's spec text is left unchanged because it is recorded in every manifest.

**Real-PostgreSQL results (this session).** 24 tests in `tests/integration-db/legacy-archive-m167/` pass on a disposable PostgreSQL 16 (17 export tests plus 7 restore tests: full restore reconciles and rolls back leaving no schema and an unchanged source, SUM per currency equals the source, `--keep` keeps a schema with real foreign keys, a pin mismatch creates nothing, a duplicate key and an orphan reference roll back and are reported by SQLSTATE only, a corrupted value is caught by the checksum and total checks, an empty database restores to empty tables). As in section 12 this ran through a Prisma client without the Rust engine because `binaries.prisma.sh` is blocked in the sandbox; **B8 stays open** until `npm run test:integration:db` is run where the engine can be downloaded.
